# Compute Service

Обчислювальний сервіс для виконання алгоритмів над графами та мережами.

Першим алгоритмом, який необхідно реалізувати, є **алгоритм Мінті** для знаходження найкоротших шляхів.

У майбутньому сервіс повинен підтримувати інші алгоритми, зокрема **алгоритм Форда–Фалкерсона** для знаходження максимального потоку та мінімального перерізу.

Архітектура повинна дозволяти додавати нові алгоритми без переписування існуючої системи.

---

# 1. Мета

Compute Service повинен:

* приймати нормалізоване представлення графа від Backend;
* виконувати обраний алгоритм;
* повертати результат обчислення;
* за необхідності повертати покроковий процес виконання;
* надавати стабільний API для Backend;
* запускатися як окремий Docker-контейнер;
* підтримувати додавання нових алгоритмів.

Перший етап:

> Методом Мінті знайти найкоротші шляхи до кожної з вершин мережі з початком у вершині 1.

Майбутній етап:

> Методом Форда–Фалкерсона знайти максимальний потік та мінімальний переріз на мережі.

# 3. Розподіл відповідальності

## Frontend

Frontend відповідає за:

* введення графа;
* вибір алгоритму;
* запуск обчислення;
* відображення графа;
* візуалізацію процесу виконання;
* відображення результату.

Frontend **не повинен реалізовувати алгоритми**.

---

## Backend

Backend відповідає за:

* HTTP API;
* авторизацію;
* бізнес-логіку;
* валідацію зовнішніх запитів;
* нормалізацію даних графа;
* взаємодію з Compute Service;
* передачу задачі через gRPC;
* отримання результату;
* передачу результату Frontend.

Backend не повинен знати внутрішню реалізацію алгоритмів.

---

## Compute Service

Compute Service відповідає за:

* алгоритми;
* computational logic;
* обробку графів;
* виконання алгоритмів;
* формування результатів;
* формування execution trace;
* validation обчислювальних даних;
* gRPC API;
* Docker-контейнеризацію.

---

# 4. Вхідні дані

Backend передає Compute Service **нормалізоване представлення графа**.

Базовий формат:

```json
{
  "vertices": 5,
  "edges": [
    {
      "from": 1,
      "to": 2,
      "weight": 5
    },
    {
      "from": 1,
      "to": 3,
      "weight": 8
    },
    {
      "from": 2,
      "to": 4,
      "weight": 7
    }
  ],
  "source": 1
}
```

### Поля

| Поле             | Опис                    |
| ---------------- | ----------------------- |
| `vertices`       | Кількість вершин графа  |
| `edges`          | Список ребер            |
| `edges[].from`   | Початкова вершина ребра |
| `edges[].to`     | Кінцева вершина ребра   |
| `edges[].weight` | Вага ребра              |
| `source`         | Початкова вершина       |

Compute Service не повинен залежати від того, як користувач вводив граф.

Frontend може використовувати:

* таблицю;
* матрицю;
* графічний редактор;
* JSON;
* інший UI.

Backend перетворює ці дані у єдиний формат перед передачею Compute.

---

# 5. Внутрішнє представлення графа

Формат, який передає Backend, є **зовнішнім контрактом**.

Compute Team самостійно визначає оптимальне внутрішнє представлення графа.

Наприклад:

```text
External Graph
      │
      ▼
Graph Parser
      │
      ▼
Internal Graph Model
      │
      ▼
Algorithm
```

Не потрібно змушувати алгоритм працювати безпосередньо з JSON або protobuf-моделлю.

Це дозволяє кожному алгоритму використовувати оптимальні структури даних.

---

# 6. Розширюваність

Compute Service повинен бути спроєктований як **розширювана платформа для алгоритмів**.

Поточний стан:

```text
algorithms/
└── minty/
```

Майбутній стан:

```text
algorithms/
├── minty/
├── ford_fulkerson/
└── ...
```

Додавання нового алгоритму повинно переважно складатися з:

1. реалізації нового алгоритму;
2. визначення необхідних input parameters;
3. визначення result model;
4. реалізації execution trace;
5. реєстрації алгоритму;
6. додавання тестів.

Не повинно бути необхідності переписувати вже реалізовані алгоритми або transport layer.

---

# 7. Вибір алгоритму

Compute Service повинен отримувати інформацію про алгоритм, який необхідно виконати.

Концептуальний запит:

```json
{
  "algorithm": "minty",
  "graph": {
    "vertices": 5,
    "edges": [
      {
        "from": 1,
        "to": 2,
        "weight": 5
      }
    ],
    "source": 1
  },
  "options": {
    "include_steps": true
  }
}
```

У майбутньому:

```json
{
  "algorithm": "ford_fulkerson",
  "graph": {},
  "options": {
    "include_steps": true
  }
}
```

Бажана архітектура:

```text
ComputeRequest
      │
      ▼
Algorithm Dispatcher
      │
      ├── minty
      │
      ├── ford_fulkerson
      │
      └── future algorithms
```

Backend не повинен створювати окремий transport layer для кожного алгоритму без необхідності.

---

# 8. Algorithm Contract

Кожен алгоритм повинен мати чіткий внутрішній контракт.

Концептуально:

```text
Algorithm
├── Input
├── Validation
├── Execution
├── Result
└── Execution Trace
```

Наприклад:

```text
MintyAlgorithm
    Input
      ↓
    Execute
      ↓
    MintyResult
      +
    ExecutionTrace
```

Майбутній:

```text
FordFulkersonAlgorithm
    Input
      ↓
    Execute
      ↓
    MaxFlowResult
      +
    ExecutionTrace
```

Не потрібно створювати один універсальний result object, який намагається описати результати всіх можливих алгоритмів.

Результат повинен бути специфічним для алгоритму.

---

# 9. Результат алгоритму Мінті

Для Мінті необхідно повертати щонайменше:

* початкову вершину;
* найкоротшу відстань до кожної вершини;
* інформацію про недосяжні вершини;
* маршрут до вершини, якщо це передбачено реалізацією.

Концептуально:

```json
{
  "source": 1,
  "distances": {
    "1": 0,
    "2": 5,
    "3": 8,
    "4": 12
  },
  "paths": {
    "1": [1],
    "2": [1, 2],
    "3": [1, 3],
    "4": [1, 2, 4]
  }
}
```

Фінальний формат визначається gRPC contract.

---

# 10. Execution Trace

Compute Service повинен підтримувати можливість повернення **покрокового процесу виконання алгоритму**.

Це необхідно для візуалізації на Frontend.

Загальний flow:

```text
Input
  ↓
Step 1
  ↓
Step 2
  ↓
Step 3
  ↓
...
  ↓
Final Result
```

Для Мінті execution step може містити:

```text
Step
├── current vertex
├── visited vertices
├── current distances
└── current paths
```

Для Ford–Fulkerson у майбутньому:

```text
Step
├── augmenting path
├── residual capacity
├── flow changes
└── current total flow
```

Execution trace є частиною обчислювального результату та формується Compute Service.

Frontend не повинен самостійно відтворювати алгоритм.

---

# 11. Режими виконання

Бажано підтримати два режими.

### Normal

Повертається тільки кінцевий результат:

```text
include_steps = false
```

### Visualization

Повертається результат та execution trace:

```text
include_steps = true
```

Це дозволяє використовувати один Compute Service як для звичайних обчислень, так і для демонстрації роботи алгоритму.

---

# 12. gRPC API

Для комунікації між Backend та Compute Service використовується:

**gRPC + Protocol Buffers**

Концептуально:

```text
ComputeService
    │
    └── Execute(...)
```

Запит:

```text
ComputeRequest
├── algorithm
├── graph
└── options
```

Відповідь:

```text
ComputeResponse
├── status
├── result
└── execution_trace
```

Фінальний `.proto` контракт необхідно узгодити між Backend Team та Compute Team.

### Важливо

gRPC contract є зовнішньою межею Compute Service.

Backend не повинен залежати від:

* внутрішніх класів;
* внутрішніх структур даних;
* конкретної мови програмування;
* конкретної реалізації алгоритму.

---

# 13. Validation

Compute Service повинен перевіряти отримані дані перед виконанням алгоритму.

Необхідно перевіряти щонайменше:

* коректність кількості вершин;
* існування вершин, вказаних у ребрах;
* коректність `source`;
* коректність ребер;
* допустимість значень ваг;
* відповідність графа вимогам конкретного алгоритму.

При цьому:

**Backend validation** відповідає за зовнішній API.

**Compute validation** відповідає за коректність обчислювальних даних.

---

# 14. Error Handling

Необхідно мати структуровану систему помилок.

Мінімально:

```text
InvalidRequest
InvalidGraph
UnsupportedAlgorithm
InvalidAlgorithmInput
AlgorithmExecutionError
InternalError
```

Наприклад:

```text
algorithm = "unknown"
        ↓
UnsupportedAlgorithm
```

або:

```text
invalid graph
        ↓
InvalidGraph
```

Не слід повертати внутрішні stack traces або implementation details через API.

---

# 15. Тестування

Кожен алгоритм повинен мати власний набір тестів.

Для Мінті необхідно перевірити:

1. простий граф;
2. декілька можливих шляхів;
3. недосяжні вершини;
4. одну вершину;
5. декілька вершин;
6. шлях через декілька проміжних вершин;
7. граничні випадки;
8. некоректні вхідні дані.

У майбутньому Ford–Fulkerson повинен мати окремий набір тестів.

Необхідно розділяти:

```text
Algorithm Tests
       +
Integration Tests
       +
gRPC Tests
```

# 18. Docker

Compute Service запускається як окремий Docker-контейнер.

Загальна структура:

```text
Docker Compose
│
├── frontend
├── backend
├── compute
└── database
```

Backend взаємодіє з Compute через внутрішню Docker network:

```text
backend → compute:50051
```

Не використовувати `localhost` для звернення Backend до Compute Service всередині Docker Compose.

Конфігурація портів та інших параметрів повинна здійснюватися через environment variables.

# 19. Майбутній Ford–Fulkerson

Архітектура першої версії повинна враховувати майбутню реалізацію:

> Методом Форда–Фалкерсона знайти максимальний потік та мінімальний переріз на мережі.

При додаванні Ford–Fulkerson не повинно бути необхідності:

* переписувати Backend;
* створювати новий Compute Service;
* переписувати gRPC transport;
* змінювати Docker architecture;
* переписувати Мінті.

Очікуваний стан:

```text
                    Compute Service
                           │
                  Algorithm Dispatcher
                    ┌──────┴──────┐
                    │             │
                  Мінті     Ford-Fulkerson
                    │             │
                    ▼             ▼
                 Result        Result
                    │             │
                    └──────┬──────┘
                           ▼
                    ComputeResponse
```

Для Ford–Fulkerson результат повинен підтримувати щонайменше:

* максимальний потік;
* мінімальний переріз;
* інформацію для візуалізації;
* execution trace.

# 22. Основний принцип

Compute Service — це не реалізація одного конкретного алгоритму.

Це **розширювана платформа для виконання алгоритмів над графами та мережами**.

Мінті є першим алгоритмом.

Ford–Fulkerson є наступним.

Нові алгоритми повинні додаватися без руйнування існуючої архітектури.

Основна межа системи:

```text
Backend
    │
    │ gRPC
    ▼
Compute Service
    │
    ▼
Algorithm
    │
    ├── Result
    └── Execution Trace
```

**Backend відповідає за API та бізнес-логіку.
Compute відповідає за обчислення.
Frontend відповідає за взаємодію з користувачем та візуалізацію.**
